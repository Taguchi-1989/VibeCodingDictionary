# モデルカードの読みどころ

巻末付録の 4 枚目です。前の 3 枚が「規格を見比べる」「導入の段を追う」ページなのに対して、こちらは **モデルを選ぶときに、何が書いてあるはずで、どこから読むのか**を 1 枚にします。

肝は 1 行です。**できることではなく、できないことが書いてある欄から読みます。**

本ファイルはデザイン担当向けのレイアウト指示書として扱います。左ページに 9 項目の表、右ページに読む順と本文を置きます。本編の J-143 モデルカードが「それが何か」を扱い、この付録は「どう読むか」に徹します。

## 左ページの表（9 項目）

### 表の狙い

Mitchell ら（2019 年）の "Model Cards for Model Reporting" が挙げる 9 項目を、**順番どおりに全部**並べます。読者が実物のモデルカードを開いたとき、目次として突き合わせられる状態にするのが目的です。

### 項目と中身

| 項目（原語） | 中身 | 書かれ方の例 |
| :-- | :-- | :-- |
| モデルの詳細<br>*Model Details* | 誰が、いつ、どのバージョンを作ったか | 「○○社、2026-03 公開、v1.2」 |
| **意図された用途**<br>***Intended Use*** | **何のために作ったか。想定していない用途も書く** | **「社内文書の要約向け。医療・法務の判断には使わない」** |
| 要因<br>*Factors* | 性能が変わる条件（人・機材・環境など） | 「文書の長さ、専門用語の多さで変わる」 |
| 指標<br>*Metrics* | どの物差しで測ったか | 「要約の正確さを人手評価で判定」 |
| 評価データ<br>*Evaluation Data* | 何を使って測ったか | 「社内文書 500 件（2025 年分）」 |
| 学習データ<br>*Training Data* | 何を使って学んだか | 「公開コーパス ＋ 社内文書」 |
| **定量分析**<br>***Quantitative Analyses*** | **条件ごとの性能。平均は良くてもここだけ悪い、が見える** | **「全体 82%、専門用語の多い文書 61%」** |
| 倫理的考慮<br>*Ethical Considerations* | 想定される害 | 「特定の書式で誤りが増える恐れ」 |
| **注意と推奨**<br>***Caveats and Recommendations*** | **使う側への申し送り** | **「重要な判断の前に原文を確認すること」** |

### 表を作るときの注意

- **9 行を減らさないでください。** 実物と突き合わせる目次が役割なので、抜けがあると使えなくなります
- **太字の 3 行（意図された用途・定量分析・注意と推奨）だけ強く見せてください。** 非エンジニアが最初に読むべき欄です
- **原語（Intended Use など）は必ず併記してください。** 実物のモデルカードはたいてい英語なので、**日本語だけだと突き合わせられません**。項目名の下に小さく置きます
- **3 列目の「書かれ方の例」がこのページの肝**です。項目名と説明だけでは、実際に何が書いてあるのか想像がつきません

## 実物はどう書かれているか（Hugging Face の場合）

**モデルカードの形は決まっていません。** 論文（Mitchell ら 2019）が定めているのは**項目**であって、ファイル形式ではないからです。Web ページとして公開されるものも、単独の文書として配られるものもあります。

ここでは、いま最も広く使われている **Hugging Face の書き方**を例にします。リポジトリに置いた **1 枚の `README.md`** で、上に **YAML の見出し（メタデータ）**、その下に **本文（9 項目に対応する文章）**、という 2 段構えです。

### 上段：YAML の見出し（機械が読む欄）

```yaml
---
library_name: transformers
pipeline_tag: text-generation      # このモデルは何をするものか
language:
  - ja
  - en
base_model:
  - org-name/base-model-name       # 何をもとに作ったか
license: apache-2.0
tags:
  - pytorch
---
```

**機械が読んで一覧・絞り込みに使う欄**です。用途・対応言語・ライセンス・派生元がここで分かります。**「どのモデルから派生したか（`base_model`）」は、責任の追跡（J-150 トレーサビリティ）の出発点**になります。

### 下段：本文（人が読む欄）

```markdown
## Model Details
作成者・公開日・バージョン・モデルの種類

## Intended Use
**想定する用途**：日本語の社内文書の要約
**想定しない用途**：医療・法務など、誤りが重大な結果を招く判断

## Factors
入力の長さ、専門用語の多さ、文書の形式で性能が変わります

## Metrics / Evaluation Data / Training Data
何を、何で測ったか

## Quantitative Analyses
条件ごとの結果（全体 82%、専門用語の多い文書 61% など）

## Ethical Considerations / Caveats and Recommendations
**長い文書では要約が抜け落ちることがあります。重要な判断の前に原文を確認してください**
```

### 読むときの目のつけどころ

- **`Intended Use` の「想定しない用途」**が、いちばん実務に効きます。ここに自分の用途が入っていたら、性能表を見るまでもありません
- **`Quantitative Analyses` の条件別**を見ます。全体の点数だけ高くて、自分が扱う条件で落ちている、というのがよくある形です
- **書式は揃っていません。** 9 項目すべてが埋まっているとは限らず、見出し名も統一されていません。**空欄そのものが情報**だと考えてください

## 右ページの図（読む順）

上から 1・2・3 と番号を振った矢印で、**意図された用途 → 注意と推奨 → 定量分析**の順に読むことを示します。性能表（指標・評価データ）は 4 番目に置きます。

## 読み方

モデルカードは、モデルの取扱説明書です。**性能の高さは各社が良く見せますが、「意図された用途」と「注意と推奨」は、作った側が自分で置いた制約**です。実務では、こちらのほうが効きます。

読む順は 3 つで足ります。**何のために作られたか**を見て、自分の用途がそこに入っているかを確かめます。次に**注意と推奨**を見て、避けるべき使い方を拾います。最後に**定量分析**を見て、自分が扱う条件で性能が落ちていないかを確かめます。平均点だけを見ていると、ここで落ちます。

**2026 年に位置づけが変わりました。** 高リスクの用途では、技術文書をそろえることが任意ではなくなっています。**ただし「モデルカードを出せば足りる」わけではありません。** 規制が求める技術文書はもっと広く、システム全体の記述・リスク管理・妥当性確認・運用の監視などを含みます。モデルカードはその一部を担う様式のひとつ、という位置づけです。

それでも、**「学習させたので大丈夫です」では通らず、どういう条件で、どこまでが限界かを示す**という方向は共通しています。読む側にとっては、そこが確かめどころです。

## 本編への案内

- **J-143 モデルカード** — この様式そのものの説明
- **J-139 説明可能性** — 個々の出力がなぜそうなったかを示す話。モデルカードはモデル全体の説明書で、層が違います
- **G-50 Evals** — 他人が測った点数ではなく、自分の仕事で測り直す側
- **J-58 EU AI Act** — 技術文書が要求になる背景
- **J-147 データ品質** — 学習データ・評価データの欄の裏側にある要求
