# コードレビュー

## tagline

書いた変更を人が読み、取り込む前に問題がないか確かめる工程です。

<!-- ━━━━━━━━ 左ページ ━━━━━━━━ -->

## 何をしてくれるか

自分以外の人が書いた変更を読み、動くかどうかだけでなく読みやすさや想定外の入力への強さ、既存の作りとの整合まで確かめます。GitHub では Pull Request の画面で指摘や修正のやり取りをしてから本流に取り込みます。

## どこで出会うか

AI がコードを書いた場面でも、取り込む前に人が見るという関門は基本的に残ります。逆に AI にレビューを任せて一次チェックに使う場面も増えており、両方の使い方に出会います。

## メイン図

### 図の狙い

AI が書いたコードでも、人が確かめてから取り込むという関門が残ることを示します。

### C. 概念図（figure_type: workflow）

- 中心に置く概念: コードレビュー（読んで確かめる工程）
- 周辺の要素: AI が書いた変更、レビュアー、指摘コメント、承認、本流への取り込み
- 関係の描き方: 変更が左から流れてきて、レビュアーの確認を経てから右の本流へ合流する矢印

## 会話での使い方例

「AI が書いたコードでも、コードレビューは人の目を通しますよね。」

## この用語の見どころ

### 1. 役割

変更を取り込む前に、人や AI が中身を確認する工程です。

### 2. うれしさ

バグや設計の乱れを取り込む前に見つけられます。

### 3. 注意点

指摘の言い方がきついと書き手との関係がぎくしゃくします。

### 4. どこで役立つか

GitHub の PR 画面で日常的に使われています。

### 5. はじめに

まずは小さな変更から人に見てもらう習慣をつけます。

### 6. 深掘り先

レビュー観点、チェックリスト、AI レビューツール

## 開発フローでの位置（必須）

1. 変更を書く — 作業ブランチで機能追加や修正をコードにします
2. Pull Request を作る — 変更をまとめて提出します
3. レビューを受ける — 人や AI が指摘やコメントを返します
4. 修正して再提出する — 指摘を反映し、再確認を依頼します
5. 承認してマージする — 問題がなければ変更が取り込まれます

## 誌面ポンチ絵メモ

### メイン図（左ページ中段 / figure_type: workflow）

- 描く内容: 左に AI エージェントがコードを書いているアイコン、中央に「コードレビュー」のカード（差分と指摘コメントの吹き出し）、右に人が確認して承認マークを出し、その先に本流のブランチへ合流する矢印

## コミュニティ補完メモ

- H-2 ペアプログラミングとの住み分け：H-2 は「一緒に書きながらその場で見る」進め方、H-4 は「書き終わったものを後から読んで見る」進め方。同時にレビューが起きる点は共通するが、H-4 はレビューが独立した工程として切り出されている場合を扱う
- F-61 Pull Request との住み分け：レビューの画面操作・本文の書き方は F-61 に譲り、本エントリは「なぜレビューという工程が要るのか」「AI が書いたコードでも人が見るのか」という考え方を扱う
- AI にレビューを任せる使い方（自動指摘ツールなど）は総論のみ触れ、個別ツールの説明は各サービスエントリに譲る

## 備考

AI が書いたコードをそのまま取り込まず、人が読んで確認してから取り込む運用が多くの現場で基本とされています。一方で AI にレビューをさせて一次チェックに使う動きも広がっており、どちらか一方に決まっているわけではありません。
