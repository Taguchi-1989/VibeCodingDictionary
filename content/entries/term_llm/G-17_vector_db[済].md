# ベクトル DB

## tagline

文章を意味ベクトルに変換して保存し、意味の近さで検索できるデータベースです。

<!-- ━━━━━━━━ 左ページ ━━━━━━━━ -->

## 何をしてくれるか

文章を Embedding（G-16）で数値ベクトルに変換して保存し、似た意味のものを高速に探し出します。RAG（G-15）が資料を探す部分は、多くの場合このベクトル DB が担っています。

## どこで出会うか

社内文書を検索させる RAG（G-15）を組むときや、似た商品・記事を探すレコメンド機能で使われます。PostgreSQL に pgvector を足すだけで試せることもあります。

## メイン図

### 図の狙い

文章がベクトルに変換されて DB に貯まり、質問に近いものだけが取り出される様子を示す。

### C. 概念図（figure_type: structure）

- 中心に置く概念: ベクトル DB（ベクトルが並んだ棚）
- 周辺の要素: 登録される文書ベクトル群、質問ベクトル、近いものを選ぶ検索、離れたものは無視される様子
- 関係の描き方: 質問ベクトルから棚の中の近い点へ矢印。遠い点は薄く描いて対比する

## 会話での使い方例

「PostgreSQL に pgvector を足すだけでベクトル DB として使えます。」

## この用語の見どころ

### 1. 役割

文章の意味ベクトルを保存し、近いものを高速に探します。

### 2. うれしさ

言い回しが違っても、意味が近ければ見つけ出せます。

### 3. 注意点

件数が増えるほど重くなり、変換モデルを変えると全件作り直しです。

### 4. どこで役立つか

社内文書検索や商品レコメンドの土台として使われます。

### 5. はじめに

まずは Postgres 拡張の pgvector から触るとつかめます。

### 6. 深掘り先

RAG（G-15）、Embedding（G-16）、PostgreSQL（F-120）

## 開発フローでの位置（必須）

1. 選定 — Postgres拡張か専用DBか、マネージドかを要件で選びます
2. 構築 — pgvector拡張や専用サービスでインデックスを用意します
3. データ登録 — Embedding済みのベクトルをDBに書き込みます
4. 検索 — 質問をベクトル化し、近いものをDBから取り出します
5. 運用 — 件数が増えたら索引方式やスペックを見直します

## コミュニティ補完メモ

- RAG（G-15）との住み分け：RAG は「質問 → 検索 → 注入 → 回答」という流れ全体を扱う。ベクトル DB はそのうち検索を担うストレージ層に絞る
- Embedding（G-16）との住み分け：Embedding は文章をベクトルに変換する仕組みそのもの。ベクトル DB はその変換結果を保存・検索する箱として説明を分ける
- PostgreSQL（F-120）との住み分け：pgvector は PostgreSQL に載せる拡張機能。PostgreSQL 本体の説明は F-120 に譲り、本エントリでは「選択肢の 1 つ」として触れるだけにとどめる
- 製品名を出す際は優劣を断定せず、「既に Postgres があるなら pgvector」「運用を任せたいならマネージド」「速度や絞り込みを詰めたいなら専用 OSS」という選び方の軸で書く（ブリーフの指示どおり）

## 備考

- 選び方の軸はおおむね 3 通り。既に PostgreSQL を使っているなら拡張機能の pgvector を載せる、運用を任せたいなら Pinecone や Qdrant Cloud のようなマネージドサービス、自前で速度や絞り込みを詰めたいなら専用の OSS（Qdrant / Milvus 等）を自前運用する、という選び方になる
- 登録件数が数万〜数十万件程度であれば、専用のベクトル DB を新しく導入しなくても pgvector 等で足りることが多い
- 製品名・料金体系は変わりやすい時変情報のため、evaluation_date（2026-08-10）を基準に読み、導入前に最新情報を確認すること
- 一度入れて終わりではない。元の文書を直したらその部分は入れ直しになり、**変換に使う Embedding モデルを別のものに変えた場合は、過去に入れた分もすべて作り直しになる**（モデルが違うベクトル同士は比べられないため）。運用の手間として最初に見積もっておく点
- 逆に、言葉の使われ方が世の中で変わっても、既に保存したベクトルが自動で変化することはない。作り直したときに初めて反映される
