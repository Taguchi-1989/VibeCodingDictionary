# JSON Schema

## tagline

データの必須キーや型を、JSON 自身の書式でルール化する仕様です。

<!-- ━━━━━━━━ 左ページ ━━━━━━━━ -->

## 何をしてくれるか

JSON データのキー名や型、とりうる値といった「形のルール」を、JSON 自身の書式で書き表します。作ったスキーマと実データを照らし合わせれば、形が崩れていないかを機械的に検証できます。

## どこで出会うか

AI に「この形式で答えて」と指示する Structured Outputs（構造化出力）や、MCP のツール定義、API のリクエスト・レスポンス検証など、機械同士が形を約束し合う場面で登場します。

## メイン図

### 図の狙い

ルールブック（スキーマ）と実データを照らし合わせ、条件を満たせば OK、満たさなければ NG が返る検証の流れを直感で掴んでもらいます。

### C. 概念図（figure_type: structure）

- 中心に置く概念: JSON Schema（ルールブック）
- 周辺の要素（3〜6個）: 必須キー、型（文字列・数値など）、許容値、実データ、検証結果（OK / NG）
- 関係の描き方（矢印・包含・比較）: ルールブックから実データへ矢印を伸ばし、条件を満たすかどうかで OK / NG の判定に分岐させる

## 会話での使い方例

「レスポンスの形は JSON Schema で縛っておくと安心です。」

## この用語の見どころ

### 1. 役割

JSON データの形を機械が検証できるルールとして定義します。

### 2. うれしさ

多くの言語で実装があり、共通の検証ルールとして使えます。

### 3. 注意点

スキーマ自体が複雑になり、書きにくく感じることがあります。

### 4. どこで役立つか

AI の出力形式や API のやり取りを検証する場面で役立ちます。

### 5. はじめに

まずは必須キーと型だけを指定するところから始めます。

### 6. 深掘り先

Draft 2020-12、Zod、Structured Outputs。

## 開発フローでの位置（必須）

1. 形を決める — 必須キーと型、許容する値をリストアップする
2. スキーマを書く — JSON Schema や Zod でルールをコードにする
3. データを検証する — 受け取った値がルールに沿うか確認する
4. AI の出力を縛る — LLM の返答形式をスキーマで指定する

## コミュニティ補完メモ

- F-8 JSON との住み分け：JSON はデータ形式そのもの、JSON Schema はその形式が「正しい形か」を検証するためのルール表記。JSON の基本構造（オブジェクト・配列など）の説明は F-8 に譲る。
- F-211 Zod との住み分け：Zod は TypeScript でスキーマを書くためのライブラリで、JSON Schema と相互変換できる場面もある。書き味やコード上の使い勝手は F-211 に譲り、本エントリは仕様そのものの説明にとどめる。
- F-212 OpenAPI との住み分け：OpenAPI は API 全体（エンドポイント・パラメータ・レスポンス）の取扱説明書で、そのレスポンスの形の記述に JSON Schema の考え方を使う。API 全体の設計は F-212 に譲る。
- F-213 API との住み分け：API は「窓口」という概念そのもの、JSON Schema はやり取りする中身の形を決める規格。F-213 側でも深掘り先として案内済み。
- G-48 Structured Outputs との住み分け：LLM に決まった形で答えさせる仕組みの詳細は G-48 に譲り、本エントリでは「共通語として JSON Schema が使われる」という接点だけに触れる。
