# API

## tagline

Application Programming Interface の略。ソフト同士をつなぐ窓口です。

<!-- ━━━━━━━━ 左ページ ━━━━━━━━ -->

## 何をしてくれるか

外部のソフトやサービスが持つ機能を、決まった手順で呼び出せる窓口です。内部の仕組みを知らなくても、指定の形式でお願いすれば、対応する形式で結果が返ってくることが保証されます。

## どこで出会うか

Web の API はリクエストを送るとレスポンス（多くは JSON）が返る形が基本で、宛先となるエンドポイント・呼び出し方法・認証の情報がセットで語られます。AI サービスも API 経由で自分のアプリに組み込めます。

## メイン図

### 図の狙い

API を「窓口」として描き、外部の機能へリクエストを送るとレスポンスが返ってくる一往復の流れを直感で掴んでもらいます。

### C. 概念図（figure_type: structure）

- 中心に置く概念: 窓口としての API（受付カウンター）
- 周辺の要素（3〜6個）: リクエスト、レスポンス、エンドポイント、認証、JSON
- 関係の描き方（矢印・包含・比較）: 利用者からリクエストの矢印を窓口へ、窓口からレスポンスの矢印を利用者へ返す往復矢印

## 会話での使い方例

「この機能、API 経由で外部サービスと連携すれば実現できますよ。」

## この用語の見どころ

### 1. 役割

外部の機能を決まった形で呼び出す窓口です。

### 2. うれしさ

内部の仕組みを知らなくても機能を使えます。

### 3. 注意点

認証やレート制限など呼び出し条件があります。

### 4. どこで役立つか

AI サービスを自分のアプリに組み込む場面で使います。

### 5. はじめに

エンドポイントとメソッドの確認から始めます。

### 6. 深掘り先

REST、エンドポイント、認証。

## 開発フローでの位置（必須）

1. API 探す — 使いたいサービスの API ドキュメントを確認する
2. 認証設定 — API キーなど認証情報を取得して設定する
3. リクエスト送信 — エンドポイントに決まった形式でデータを送る
4. レスポンス処理 — 返ってきたデータをアプリの中で使う
5. エラー処理 — レスポンスのステータスを見て失敗時の処理を書く

## 誌面ポンチ絵メモ

### メイン図（左ページ中段 / figure_type: structure）

- 描く内容: 受付カウンター（窓口）のイラスト。カウンターの奥に「機能」を持つサーバー、手前に利用者が立ち、紙（リクエスト）を渡すと窓口から紙（レスポンス）が返ってくる一往復の流れ
- 登場人物: カウンターに紙を渡す非エンジニアの人物 1 人、窓口の奥のサーバー（擬人化せず箱でよい）
- 吹き出し・心の声: 「この形式でお願いすれば、この形式で返してもらえます。」
- 中央に置くキーワード/ラベル: リクエスト → API（窓口） → レスポンス

### 6視点アイコン（右ページ上段）

- 共通アイコン流用

### 開発フロー図（右ページ下段）

- Step 1 のアイコン/絵柄: 虫眼鏡（API 探す）
- Step 2 のアイコン/絵柄: 鍵（認証設定）
- Step 3 のアイコン/絵柄: 送信矢印（リクエスト送信）
- Step 4 のアイコン/絵柄: 受信トレイ（レスポンス処理）
- Step 5 のアイコン/絵柄: 警告マーク（エラー処理）
- 矢印で示す流れの意図: 探す → 認証 → 送信 → 受け取り → 例外対応 の 5 ステップ

## コミュニティ補完メモ

- F-210 JSON Schema・F-212 OpenAPI との住み分け：本エントリは「API とは何か」という土台のみを扱い、リクエスト・レスポンスの厳密な形式定義（JSON Schema）や API 全体の仕様書の書き方（OpenAPI）には踏み込まない。両エントリへの深掘り先として案内する想定。
- G-33 Function Calling との住み分け：AI が API を呼び出す仕組みの詳細は G-33 に譲り、本エントリでは「API 越しに機能を呼べる」という一般像だけを扱う。
- F-214 API キーとの住み分け：認証の仕組み自体は F-214 に譲り、本エントリでは「認証が必要になることがある」という事実だけに触れる。
