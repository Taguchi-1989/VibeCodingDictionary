## tagline

検証可能なゴールを永続ループへ翻訳し、条件成立まで自律実行させる仕組みと、その暴走を防ぐ制御（ガードレール）の総称です。

<!-- ━━━━━━━━ 左ページ ━━━━━━━━ -->

## 何をしてくれるか

「ゴール → コマンド → ループ」という 3 段の翻訳です。人間は検証可能なゴール（テスト通過などで機械的に判定できる完了条件）を上流で 1 回だけ指定し、それを永続ループへ翻訳します。ループは毎周回で完了判定を行い、条件が満たされるまで自律実行を続けます。ralph（OMC の `ralph`）や `ultrawork` は、この仕組みの具体的な実装です。手動で「1 回頼んで待って次を頼む」（prompt-wait-prompt）を繰り返す運用を、条件が揃うまで回り続ける自律ループに置き換えます。

## どこで出会うか

Claude Code で `ralph` や `ultrawork` を起動し、「テストが全部通るまで直し続けて」のような検証可能ゴールを渡す場面で出会います。LLM（大規模言語モデル）には本来「done（完了）」という概念がありません。1 回の応答が終わったところで自分から止まる保証はなく、外側にループとガードレールを設計して初めて「終わり」が生まれます。ここが本エントリの主戦場で、複数エージェントの役割分担そのものを扱う G-43 オーケストレーションとは焦点が異なります。

## メイン図

### 図の狙い

「ガードレールなしで回り続けるループ」と「ガードレール付きで安全に止まるループ」を対比し、どこで・何が暴走を食い止めるのかを一目で示す。

## 会話での使い方例

「ralph は無進捗検知と circuit breaker がないと、silent failure に気づけないんですよね。」

## この用語の見どころ

### 1. 役割

検証可能ゴールを永続ループへ翻訳し、条件成立まで自律実行させる制御の仕組みです。

### 2. うれしさ

手動の prompt-wait-prompt をなくし、人が離席していても作業が進み続けます。

### 3. 注意点

LLM に done の概念がなく、放置すると暴走やコスト爆発が起きやすいです。

### 4. どこで役立つか

ralph・ultrawork など長時間の自律実行タスク全般で効きます。

### 5. はじめに

「3 つの敵（終わりが分からない・文脈が溢れる・コストが爆発）」を押さえると芯が掴めます。

### 6. 深掘り先

無進捗検知、circuit breaker、goal drift、検証可能な完了条件

## 開発フローでの位置（必須）

1. ゴール設定 — テスト通過など検証可能な完了条件を上流で 1 回だけ指定する
2. ループ翻訳 — ゴールを永続ループへ落とし、毎周回で完了判定を行う
3. ガードレール設置 — 反復上限・コスト予算・無進捗検知・circuit breaker（連続失敗で遮断する仕組み）を組み込む
4. 自律実行 — 条件成立まで回し続け、不可逆操作の手前だけ人間チェックポイントを挟む
5. 監視 — goal drift（目標のすり替わり）や silent failure（進捗なく回り続ける失敗）を後から検知する

## 誌面ポンチ絵メモ

### メイン図（左ページ中段 / figure_type: structure）

- 描く内容: 上段「ガードレールなし」、下段「ガードレールあり」の 2 段比較。上段はループの矢印がぐるぐる無限に回り続け、途中で GPU/コストのメーターが振り切れる。下段は同じループに「反復上限」「コスト予算」「無進捗検知」「circuit breaker」「人間チェックポイント」の 5 つの関所（ゲートアイコン）が挟まり、条件が揃った時点でループが止まる。
- 登場人物（いれば）: 自律ループを回すエンジニア 1 名（著者の分身）。上段では暴走するメーターに焦った表情、下段では関所で止まったループを見て安堵した表情。
- 吹き出し・心の声: 「ゴールを渡して終わりじゃなかった。止まる仕組みまで自分で設計しないと、気づかず回り続けるだけなんだ」
- 中央に置くキーワード/ラベル: 「LLM に done の概念なし」「ガードレール＝暴走を防ぐ関所」「silent failure に注意」

### 開発フロー図（右ページ下段）

- Step 1 のアイコン/絵柄: ゴールを 1 枚の紙に書いて渡す手
- Step 2 のアイコン/絵柄: 紙がループの矢印へ翻訳される変換ボックス
- Step 3 のアイコン/絵柄: ループ上に並ぶ 5 種の関所ゲート

## コミュニティ補完メモ

- 同じ Lv6 シェルフ／既刊との住み分け:
  - オーケストレーション（G-43・刊行済）: 複数エージェントの役割分担・指揮系統を扱う。本エントリは単一ループでも成立する「止め方」の制御そのものに焦点を当て、複数体制の設計論とは重ならない。
  - ループエンジニアリング（総論・進化史）: ReAct から Ralph Loop に至る「敵を潰すと次の敵が出る」進化史そのものは総論側に譲り、本エントリは §3 のガードレール部分の実装論に特化する。
  - Ralph Loop: 毎周回でディスクから状態を読み文脈窓をリセットする具体的な実装。本エントリはその実装が備えるべき止め方（ガードレール）の一般論。
- スコープ境界: 本エントリは「なぜ止まらないか（done の概念なし）・何で止めるか（5 種のガードレール）・最も厄介な失敗（silent failure・goal drift）」までを担う。コンテキスト工学の中身（圧縮・メモリ・サブエージェント）は別エントリに譲る。
