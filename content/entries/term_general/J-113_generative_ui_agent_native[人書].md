## tagline

事前に組んだ画面をエージェントがその場で組み立て直す設計思想です。人間用と AI 用の UI を分けない「agent-native」が軸になります。

<!-- ━━━━━━━━ 左ページ ━━━━━━━━ -->

## 何をしてくれるか

Generative UI（GenUI、生成UI）は、静的に作り込んだ画面をやめ、AI がそのときの必要に応じて UI をその場で組み立てる考え方です。agent-native architecture（エージェント前提の設計）は、人間用の画面と AI エージェント用のインターフェースを別々に作らず、単一の共有データベース状態・アクションモデルの上に両者を載せる設計方針です。エージェントが作った提案カード（proposal card、ほぼ完成品の提案）を人間が承認・微調整するだけ、という操作の型が中心になります。

## どこで出会うか

「AI がタスクの大半を代行してくれるのに、人間はまだ従来通り画面をクリックして回っている」という違和感に触れたときに出会う概念です。SaaS（Software as a Service）の画面設計を見直す議論や、Agent Experience（AX、エージェント体験）という言葉で「検索して自分で操作する」から「複雑なミッションを自律 AI に委ねる」への移行を語る記事の中で登場します。「UI はエージェントに同意しないときだけ行く場所になる」という表現がこの流れを象徴します。

## メイン図

### 図の狙い

「人間用画面と AI 用 API を別々に作る旧来設計」と「共有状態の上で GenUI が人間にもエージェントにも同じ土台を返す agent-native 設計」を対比し、なぜ画面が固定でなくなるのかを掴んでもらう。

## この用語の見どころ

### 1. 役割

人間とエージェントが同じ状態・アクションを共有し、画面をその場で組み立て直す設計です。

### 2. うれしさ

人間は提案カードを承認・微調整するだけで済み、操作の認知負荷が下がります。

### 3. 注意点

全自動化ではなく、人間の判断と自動化のバランスを取る設計として語られています。

### 4. どこで役立つか

複雑な業務ミッションを AI に委ねたい SaaS・社内ツールの設計見直しで役立ちます。

### 5. はじめに

「人間用 UI と AI 用 UI を分けない」という一点を押さえると全体像が掴みやすいです。

### 6. 深掘り先

Agent Experience（AX）、提案カード、dashboard obsolescence、post-SaaS

## 開発フローでの位置（必須）

1. 状態の統合 — 人間の画面と AI エージェントが同じ共有データベース状態・アクションモデルを参照する設計にする
2. 提案生成 — エージェントがタスクをこなし、ほぼ完成した提案カードを組み立てる
3. UI の動的生成 — GenUI がそのときの文脈に応じて必要な画面要素だけをその場で構成する
4. 人間の承認 — 人間は提案カードを承認・微調整し、不同意のときだけ従来型の画面を開く
5. 継続運用 — 自動化と人間判断のバランスを見ながら、委ねる範囲を段階的に広げる

## 誌面ポンチ絵メモ

### メイン図（左ページ中段 / figure_type: structure）

- 描く内容: 左側「旧来設計」は人間用の画面（ブラウザ枠）と AI 用の API（別の箱）が別配線で同じデータベースに繋がっている図。右側「agent-native」は人間とエージェントの両方が 1 本の共有状態・アクションモデルの箱につながり、そこから GenUI が状況に応じて画面をその場で組み上げる矢印を描く。エージェント側からは「提案カード」が人間側へ流れ、人間はチェックマークで承認するだけの動きを添える。
- 登場人物（いれば）: 業務ツールを使うユーザー 1 名（著者の分身）。旧来設計側では複数の画面を行き来して疲れた表情、agent-native 側では提案カードにチェックを入れるだけで済み一息ついている。
- 吹き出し・心の声: 「毎回自分で画面を探して操作してたのに、承認するだけでいいなら随分違う」
- 中央に置くキーワード/ラベル: 「GenUI＝その場で組み立てる画面」「agent-native＝人間用と AI 用を分けない」「提案カード＝ほぼ完成品を承認」

### 6 視点アイコン（右ページ上段）

- 共通アイコン流用（① 共有状態の箱、② 提案カードにチェックを入れる手、を差し色で強調）

### 開発フロー図（右ページ下段）

- Step 1 のアイコン/絵柄: 人間とエージェントが 1 本の共有データベースにつながる配線図
- Step 2 のアイコン/絵柄: エージェントが組み立てる提案カード（書類アイコン）
- Step 3 のアイコン/絵柄: その場で組み上がる画面パーツ（可変ブロック）
- Step 4 のアイコン/絵柄: 承認チェックマークと「不同意のときだけ開く」旧来画面のドア
- 矢印で示す流れの意図: 状態の統合 → 提案生成 → UI の動的生成 → 人間の承認 → 継続運用、という「画面が固定物でなくなるまで」の流れ

## コミュニティ補完メモ

- 同じ Lv6 シェルフの近接語との住み分け:
  - 認知コストの定量化（J-112）: resolution velocity・UX 心理監査など「摩擦を測る」側の話。本エントリはその測定結果を受けて「画面をどう作り替えるか」という設計解の側。
  - 人間の認知ボトルネック（J-111）: 監督負担・認知過負荷という問題提起そのもの。本エントリはその解決策の 1 つとしての UI 設計論。
  - 自律ループとガードレール（J-107）: エージェントがどう動き続けるかという裏側の実装。本エントリはその成果を人間にどう見せるかという表側のインターフェース。
  - Artifact（G-36）: 会話の中でエージェントが生成する成果物の表示形式の 1 つ。本エントリの「提案カード」はその発展系として画面全体の設計思想に広げたもの。
  - LLM（J-14）: GenUI・agent-native を成立させる基盤モデル。
- スコープ境界: 本エントリは「GenUI・agent-native・提案カード・AX という語の意味とつながり」までを担う。認知負荷の測定手法や自律ループの実装詳細は各深掘りエントリに譲る。
